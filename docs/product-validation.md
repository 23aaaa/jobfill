## 建议的真人验证（尚未执行）

先招募 5–8 名正在投递、经历数量不同的求职者，使用虚构资料和自己的测试草稿，取得录屏/观察许可；不要收集身份证或完整真实简历。把同一套任务分别用 TXT 复制和插件完成，交叉安排顺序，避免熟练度只利于后一种方式。

任务覆盖：首次安装；维护基本信息；创建 3 段经历；自定义一个模块与一个分组；HTML/Excel 往返后核对；在三个招聘网站填写；故意触发超长字段/权限失效；使用手动复制兜底；导出加密备份并恢复；永久清除。

建议记录建档用时、查找字段用时、填写错误数、未保存丢失数、求助次数、导入后字符差异、退出原因。建议发布门槛为：零误填其他页面、零静默数据丢失、零未授权整库暴露；至少大多数参与者能无需指导完成主要路径。节省时间等商业宣传必须使用真实对照数据，不能把“目标减少 50% 时间”写成已经取得的效果。

## 真实平台测试（尚未执行）

至少逐一覆盖字节、阿里、美团的当前登录网申草稿页。按入口、实际 URL、浏览器版本、日期、表单控件类型、正确写入与保存回读结果记录。多段工作/实习/教育经历分别测，原生文本框成功不能推断该公司所有组件成功。不要自动提交正式申请，也不要在未许可的第三方账号中运行。

兼容性表应区分“直接填写通过”“手动复制可用”“不支持”。遇到特殊控件先提供安全兜底，再决定是否增加独立站点适配器。当前没有任何一家公司的整站兼容保证。

## 收费闭环（尚未执行）

当前产品是无账号的本地工具，可作为文件型产品分发，但没有支付接口、激活码校验或防复制机制。用户下载到的代码可被查看；不能宣传不存在的授权防盗能力。

运营者必须确定真实销售渠道、收款主体、购买者使用许可、版本升级范围、退款与技术支持流程。测试从一次真实或支付平台正式沙箱订单到文件交付、安装失败求助、退款处理的完整路径。支付渠道自己的隐私处理与本插件的本地资料处理应分别说明。

`docs/store/merchant-config.json` 与 `docs/validation/release-checklist.json` 故意保持未完成状态。补齐当前版本的脱敏证据后运行 `npm run verify:release`；门禁不会凭文案把这些项目视为已经完成。

## 发布与回滚

发布前冻结源码、重新运行测试并生成 SHA-256 清单。正式发行应将 version_name 从 rc 调整为实际版本，同时在测试与文档中更新版本。商店上传使用 manifest 位于 ZIP 根目录的扩展包，不上传包含测试、样本及运营草案的整个源码包。

首次发行不能假设覆盖了所有求职网站。公开列明实际支持范围与兜底方式。保存上一版安装包和用户可导出的 v1 文件兼容能力；紧急更新优先停止危险写入，而不是删除用户资料。后续改动云端/支付/权限时重新执行安全、隐私与商业验收。
